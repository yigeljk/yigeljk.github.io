计算机网络

数据从网卡到达应用程序的整个链路

  1. 网卡先把物理层的数据转换为以太网帧，然后通过DMA将数据拷贝到内核的网卡环形缓冲区，然后中断cpu
  2. cpu中断后，转向处理内核中的以太网帧，将数据包去帧头，去IP头，去tcp头，通过四元组对应到其socket
  3. 内核将数据拷贝到对对应socket连接的内核接受缓冲区
  4. 然后内核查看struct_socket查看该socket是否被注册到了红黑树里面，如果是，我们去将fd添加到就绪队列里面；如果不是，那么就不会去通知事件；
  5. 内核不会在这个时候遍历红黑树，因为有映射关系，红黑树只是为了更快的添加和删除fd，应用在调用epoll_ctl add,delete的时候
  6. 然后内核唤醒tomcat的监听线程，监听线程将这个socket连接的内核缓冲区的数据拷贝到用户缓冲区，并将其作为HttpServletRequest对象请求交给工作线程来处理
  7. 由工作线程执行过滤器，servlet执行后续逻辑
  • tomcat会把整个http请求全部转换为字符串，包括请求行，请求头，请求体

  • 然后封装成 HttpServletRequest 对象，再把这个 Request 对象 交给工作线程。

  • 封装 HttpServletRequest（里面存原始字节，还没解码）

    转给工作线程 → 执行 Filter（设置编码规则）

  • 工作线程拿着HttpServletRequest对象先执行过滤器，将原始字节流转换为字符流，进入DispactherServlet前端控制器，解析url，通过HandlerMapping映射到对应的Controller方法，然后执行Interceptor拦截器，进行接口校验，身份校验，然后再通过HandlerAdapter来去执行对应的Controller方法

  • 然后进入spring boot， @RequestBody如果发现请求头里面的content-Type是application/json，spring的jackon会把这个对象里面的请求体部分转换为DTO对象

实体类和DTO和数据库表和HTTP的映射关系

Linux文件系统

  • 每个进程里面有独立的文件描述符表的映射，fd->内核文件表项，每个进程最多1024个文件描述符

  • 内核文件表项有文件的权限，读写偏移量，被几个fd使用的消息，并且指向内存或者磁盘中真正的inode节点

  • inode节点存储：

    1.文件大小
    2.权限（读、写、执行）
    3.所有者、所属组
    4.时间：创建时间、修改时间、访问时间
    5.磁盘数据块指针（最关键）
    6.记录这个文件的内容存在硬盘哪几个扇区、哪几块

  • inode节点在磁盘上面，指向磁盘的真实位置；磁盘上面有真实的inode表

MySQL日志

  • 执行流程：正常执行：undo log（写磁盘）→ redo log buffer → COMMIT → redo log prepare（把核心数据刷盘） → binlog 刷盘 → redo log 刷盘（状态位） + 改 commit → 事务完成；

  • undo log（记录数据修改前的原始版本），bing log（记录数据库的行为，比如sql行为），redo log（记录数据库哪个数据页的哪个偏移量，改成了什么值）

  • 我们MySQL在执行sql的时候，首先会把旧数据写入undo log里面，然后再写入redo log里面的buffer中（未刷盘），将状态改为prepare，然后我们把修改的数据写入bing log里面（并进行刷盘），然后我们将redo log进行刷盘并且同步将redo log的状态改为commit

  • 崩溃恢复的时候，我们先检查redo log的状态，如果是commit，我们直接将redo log的数据刷到数据库的磁盘页中。如果是prepare，我们先检查bing log，binglog里面有记录的话，判断为应该提交的事务，我们会补做redo log，如果bing log里面也没有数据的话，我们会直接回滚。

  • 执行commit语句，只是开始提交，我们的事务不一定提交

  • edo log 和 binlog 的设计目标、存储格式、语义完全不同，无法从 redo log 反向生成 “合法且一致的 binlog”，所以我们先提交bing log，再提交redo log

  • redo log和bing log都是顺序写，redo log是自动循环覆盖，bing log是追加写

  • MySQL的快照读和写请求之间不会阻塞，但是当前读和写请求就会阻塞，因为如果是行读，会加行锁，如果是范围读，会加间隙锁

  • 垂直分库分表是解决解耦的问题，水平分库分表是解决单表数据量太大的问题

Redis日志

  • redis的持久化机制有AOF和RDB，RDB默认是开启的

  • AOF会保留redis执行的命令，当redis执行的命令比较多的时候，Redis会进行重写，此时redis会fork一个子进程来去重写日志，删除那些冗余的命令，这时候如果redis主线程正在进行写入操作，会出现COW（Copy On Write写时复制）会触发大量的系统调用，导致大量的内存复制，性能下降

  • RDB快照有两种创建方式，第一种，直接save，使用主线程来去创建RDB快照，但是会阻塞主线程。第二种，进行bgsave（background save），redis会fork一个子进程，子进程在后台会创建RDB快照，当fork子进程后，如果redis正在写入数据，那么会触发COW（copy on write写时复制），触发大量的系统调用来去复制内存

    • 原因：因为fork一个子进程后，父进程和子进程共享一块物理内存空间，如果一个进程要写，就会触发系统调用，进行内存复制

Java基础

多态

  • 多态的核心：同一个行为，不同的表现形式

  • 多态的分类：重载（编译时多态）和重写（运行时多态）

  • 重载调用的具体方法是在编译时期确定的（根据参数类型确定），而重写是运行的时候才知道会具体调用哪个方法

  • 重载：参数列表必须不同，返回值可以不同

  • 重写：参数列表必须相同，返回值相同或者是子类

  • 重写（运行时多态）：编译时看左边，我们重写的时候调用的方法需要看左边的父类或者接口里面是否有这个方法，如果没有，会报错，如果有，运行的时候实际执行的是右边实现类或者子类的具体方法

final关键字

  • 可以修饰类，方法，变量
  • 修饰类的话，这个类不可以被继承。比如String类设置为final，保证其功能不被子类篡改
  • 修饰方法，这个方法不可以被重写
  • 修饰变量的话
    • 如果是基本数据类型，这个变量的值不可以改变
    • 如果是引用数据类型，这个变量的引用地址不可以改变，但是对象的内容可以改变

static关键字

  • static可以修饰内部类，方法，变量

  • 静态变量，方法，和内部类可以被所有实例所共享，类加载的时候只加载一次

  • 静态方法存储在方法区里面，静态变量存储在堆内存的老年代里面（基本数据类型和引用数据类型都存储在堆里面），静态内部类的定义是存储在方法区里面，静态内部类的实例是存储在堆里面

  • 静态方法和静态变量我们不需要创建实例，直接可以通过类名来调用。创建静态内部类的实例的时候也不需要创建这个静态内部类的外部类实例，直接可以根据外部类的类名来创建它的静态内部类

    • 静态方法不可以直接调用非静态方法，必须创建这个类的实例，再进行调用

  • 非静态方法调用非静态方法，同一个类里面可以直接来调用，不同类必须创建实例才可以调用

    • 静态方法调用静态方法，可以直接通过类名来调用

  • 非静态方法调用静态方法，可以直接通过类名来调用
