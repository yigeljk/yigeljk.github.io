论之道项目

Created2026-09-05|Updated2026-09-06

根据代码阅读，你们这套系统里的「多租户隔离」主要是 分库（按租户）+ 可选分表（按学年 dataScope）+ 应用层身份与数据范围校验 组合起来的，而不是单纯在一张大表里用 WHERE tenant_id = ? 这一种模式。

1. 核心：按 tenant_id 的物理分库（ShardingSphere）

在 LzdAutoDataSourceConfig 里，当配置打开 按租户分库（Nacos 里常见的 global-database-sharding-by-tenant-id: true）时，会为 ShardingSphere 配置 默认库分片策略：分片键是列 tenant_id，算法是自定义的 LZD_DATABASE_SHARDING_BY_TENANT_ID。

​ rule.getShardingAlgorithms().put(LZD_DATABASE_NON_SHARDING, new AlgorithmConfiguration(LZD_DATABASE_NON_SHARDING, new Properties()));

​ rule.getShardingAlgorithms().put(LZD_DATABASE_SHARDING_BY_TENANT_ID, new AlgorithmConfiguration(LZD_DATABASE_SHARDING_BY_TENANT_ID, new Properties()));

​ rule.getShardingAlgorithms().put(LZD_TABLE_NON_SHARDING, new AlgorithmConfiguration(LZD_TABLE_NON_SHARDING, new Properties()));

​ rule.getShardingAlgorithms().put(LZD_TABLE_SHARDING_BY_DATA_SCOPE_ID, new AlgorithmConfiguration(LZD_TABLE_SHARDING_BY_DATA_SCOPE_ID, new Properties()));

​ // 默认分库分表规则

​ rule.setDefaultDatabaseShardingStrategy(properties.isGlobalDatabaseShardingByTenantId() ? new StandardShardingStrategyConfiguration(COLUMN_TENANT_ID, LZD_DATABASE_SHARDING_BY_TENANT_ID) : new StandardShardingStrategyConfiguration(COLUMN_TENANT_ID, LZD_DATABASE_NON_SHARDING));

​ rule.setDefaultTableShardingStrategy(properties.isGlobalTableShardingByDataScopeId() ? new StandardShardingStrategyConfiguration(COLUMN_DATA_SCOPE_ID, LZD_TABLE_SHARDING_BY_DATA_SCOPE_ID) : new StandardShardingStrategyConfiguration(COLUMN_TENANT_ID, LZD_TABLE_NON_SHARDING));

LzdDatabaseShardingByTenantIdAlgorithm 把 租户 ID 映射成 真实库名（前缀 + 从 tenantId 解析出的段，例如文档里写的 JWC.SCU → lzd_scu_jwc 这类规则），并在需要时 动态注册 指向该库的 DataSource，同时用线程变量绑定当前要连的库：

​ public String doSharding(Collection availableTargetNames, PreciseShardingValue preciseShardingValue) {

​ String tenantId = preciseShardingValue.getValue();

​ // … 计算 tdb …

​ // 当前线程的 数据源

​ String currTdb = DriverDatabaseConnectionManager.LOOKUP_KEY_HOLDER.get();

​ if (null != currTdb) {

​ return currTdb;

​ }

​ // … 若不存在则创建/注册 DataSource …

​ DriverDatabaseConnectionManager.LOOKUP_KEY_HOLDER.set(tdb);

​ DriverDatabaseConnectionManager.DATA_SOURCE_HOLDER.set(dataSources.get(storageNode));

​ return tdb;

​ }

另外，你们对 ShardingSphere 的 KernelProcessor 做了补丁：在生成执行计划后，若线程里已经指定了目标库名，会把执行单元 强制路由到该数据源，避免和默认路由不一致：

​ // LZD 修改源码

​ String tdb = DriverDatabaseConnectionManager.LOOKUP_KEY_HOLDER.get();

​ if (null != tdb && !tdb.isBlank()) {

​ result.getExecutionUnits().forEach(executionUnit -> executionUnit.setDataSourceName(tdb));

​ }

含义：租户之间在存储上首先是 不同数据库（或至少不同逻辑库映射到不同物理库），这是最强的隔离层。

2. 租户内再细分：data_scope_id 分表（学年/数据范围）

同一条业务数据在「同一租户库」里，还可能按 data_scope_id（注释里写的是类似学年 20212022）做 表级分片。是否参与由实体上的 @TableShardingByDataScopeId 以及全局开关 global-table-sharding-by-data-scope-id 等共同决定；LzdScanner.tableSharding 会为每张表挂上是否按 data_scope_id 分表的策略。

也就是说：租户 → 库；学年/数据范围 → 部分表再物理拆表，进一步减少单表数据量、避免不同学年数据混在一起。

3. 实体与查询约定：appId / tenantId / dataScopeId

所有业务表的基类 XEntity 上带有三个维度字段，语义在注释里写得很清楚：

​ public String appId = “GP”;

​ @Column(columnDefinition = “varchar(64) not null default ‘’ comment ‘所属租户ID’ “)

​ public String tenantId = “”;

​ @Column(columnDefinition = “int not null default 0 comment ‘所属租户数据范围整数：20212022、20222023’ “)

​ public int dataScopeId = 0;

分页查询封装 RPP 在构造时可以把 当前租户的 tenantId 写进 where 条件，避免漏带租户条件：

​ public RPP(@NotNull U where, @NotNull String tenantId) {

​ this(where);

​ Assert.notNull(tenantId, “tenantId must not null.”);

​ this.where.setTenantId(tenantId);

​ }

还有一些 特例基类：例如 SingleEntity 固定默认租户、不参与多租户维度；TenantInfo 把 dataScopeId 固定为 0，表示租户元数据不按学年分。

4. 请求上下文：JWT → 登录用户 → 租户信息

LzdMvcConfigurer 里：从 JWT 解析出 tenantId / userid，加载 TenantUser，并调用 lzdRestful.tenant(tenantId) 把 TenantInfo 放进 LzdUtil.TENANT_INFO_HOLDER（TransmittableThreadLocal），供后续业务使用。

这样 当前请求绑定的租户 来自已登录身份，而不是仅靠前端随意传 tenantId（内部接口另有 /inner/ 与密钥逻辑）。

5. 业务上的「数据范围」校验：@DataScope

DataScopeAspect 在带 @DataScope 的方法上，会结合 当前登录用户的 tenantId，对入参里的 dataScopeId 做 是否锁定等业务校验（例如某学年是否允许修改），这是 在库表隔离之外的权限/状态层。

小结（如何理解「多租户隔离」）

层次 机制
存储 开启全局按租户分库时，ShardingSphere 以 tenant_id 为分库键，映射到独立库名并路由连接；可选按 data_scope_id 分表。
元数据与查询 实体带 appId / tenantId / dataScopeId；分页等场景通过 RPP(where, tenantId) 等把租户条件带入查询。
请求 JWT + 拦截器设置 登录用户与租户信息 到 ThreadLocal。
业务 @DataScope 等对学年/数据范围做额外校验。

整体上，你们更接近 「租户 = 独立数据库（+ 部分表按学年再拆）」 的隔离模型，而不是所有租户共库只靠应用层 WHERE 过滤一种做法。若你需要对某条接口「隔离是否可能被绕过」做审计，可以再针对该接口看：SQL 是否总带 tenant_id、分库键是否总能从当前登录上下文得到等——当前 Ask 模式我只能做代码级说明，不改代

一、分工关系

谁负责 做什么
我们 实现 doSharding()，定义“分到哪个库”的逻辑
ShardingSphere 调用 doSharding() 拿到库名，选数据源、改写 SQL、执行、管理连接等

二、doSharding() 需要自己重写

实现 StandardShardingAlgorithm<String> 时，必须实现 doSharding()：

public class LzdDatabaseShardingByTenantIdAlgorithm implements StandardShardingAlgorithm {

​ @Override

​ public String doSharding(Collection availableTargetNames,

​ PreciseShardingValue preciseShardingValue) {

​ // 我们实现：根据 tenant_id 返回目标库名

​ String tenantId = preciseShardingValue.getValue();

​ String tdb = “…”; // 计算逻辑

​ return tdb; // 返回给 ShardingSphere

​ }

}

三、ShardingSphere 负责的部分

  1. 解析 SQL：识别分片键（如 tenant_id）
  2. 调用算法：执行 doSharding() 得到目标库名
  3. 选择数据源：根据返回的库名找到对应数据源
  4. 改写 SQL：把逻辑表名换成物理表名（如库名.表名）
  5. 执行 SQL：通过选出的数据源执行
  6. 结果合并：多库/多表时的结果合并

四、总结

  • 分库/分表的规则：由我们在 doSharding() 里实现。
  • 分库/分表的执行：由 ShardingSphere 负责。

可以理解为：我们定规则，ShardingSphere 负责执行。

表结构

根据项目代码和 Nacos 配置，这些数据库大致用途如下：

一、租户业务库（lzd_ 前缀，ShardingSphere 分库）

按 tenant_id 分库，命名规则：lzd_ + tid。

数据库 用途
lzd_lun51 主库 / 平台库。平台级数据（cfl_region、cfl_university）、租户元数据（bsl_tenant_info）、LUN51 租户业务。Nacos 中 database-name 指向此库。
lzd_szcu_jwc JWC.SZCU 租户业务库（如教务处等）。
lzd_mode_mini MINI.MODE 租户（精简版）。
lzd_mode_pro 专业版租户。
lzd_mode_ultra 旗舰版租户。
lzd_mode_yjs 研究生版租户（yjs = 研究生）。租户配置中有 databaseName: "lzd_mode_yjs"。
lzd_lun51_sales 可能是 LUN51 的销售/商务相关库，或独立租户。

二、项目级 / 模板库

数据库 用途
lzd_table_tpl 表结构模板库。Nacos 中 database-name: lzd_table_tpl 时用于 JPA DDL、建表模板。
lzd_project 项目级数据，可能存放跨租户的项目元信息。
db_project_lun51 可能是旧版或另一套的项目库。

三、功能模块库（lzd_gp_ 前缀）

按功能拆分的库，可能用于文件、表单、文档等：

数据库 用途
lzd_gp_file01 / lzd_gp_file02 文件相关数据（如分片存储）。
lzd_gp_form01 / lzd_gp_form02 表单相关数据。
lzd_gp_word01 / lzd_gp_word02 文档/Word 相关数据。

四、基础设施 / 中间件库

数据库 用途
lzd_nacos3 Nacos 配置中心/注册中心数据。项目 Nacos 配置中 db.url.0=jdbc:mysql://.../lzd_nacos3。
db_nacos / lzd_nacos 其他 Nacos 实例或环境的库。
lzd_xxljob XXL-Job 分布式任务调度，存任务配置、执行日志等。项目中有 lzd-cfl-xxljob 模块。
lun51monitor 监控相关数据（日志、指标等）。

五、旧版 / V2 租户库（db_lun51_v2_ 前缀）

数据库 用途
db_lun51_v2_hebiace_jwc V2 版河海/教务处租户。
db_lun51_v2_hebiace_xxgc V2 版河海/信息工程租户。
db_lun51_v2_jwcuestc V2 版电子科大教务处租户。
db_lun51_v2_lun51 V2 版 LUN51 主库。
db_lun51_v2_lwpy V2 版论无忧租户。
db_lun51_v2_lwpydemo V2 版论无忧演示租户。
db_lun51_v2_mode_mini/pro/ultra V2 版各模式租户。
db_lun51_v2_tpl V2 版表模板库。

六、MySQL 系统库

数据库 用途
information_schema MySQL 元数据（库、表、列等）。分库算法用 SCHEMATA 判断库是否存在。
mysql 用户、权限等系统表。
performance_schema 性能监控数据。
sys 对 performance_schema 的简化视图。

七、其他 / 可能非本项目

数据库 说明
db_123, db_ctc 测试或临时库。
db_lun51_20201026 可能是某次迁移或备份。
db_lun51_location 可能与位置/地理信息相关。
db_mooc MOOC 平台相关。
db_obedu 在线教育相关。
db_lcsl 其他项目。
db_zentao 禅道项目管理工具。

八、与 Nacos 配置的对应关系

lzd-bsl-all-dev.yml 中：

spring:

datasource:

​ host: 192.168.4.223

​ port: 3308

​ database-name: lzd_lun51 # 主库，应用启动时连接

​ database-prefix: lzd # 分库命名前缀

​ global-database-sharding-by-tenant-id: true

  • 应用启动时连接：lzd_lun51
  • 分库命名：lzd_ + 租户 tid
  • 租户库（如 lzd_szcu_jwc）在首次访问时由 ShardingSphere 动态创建数据源并连接
